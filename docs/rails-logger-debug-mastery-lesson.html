POTEPAN / RAILS / LOGGER

Rails.logger.debugを
自分で使いこなす

「ログに出す」と覚えるだけで終わらせず、何を・どこで・どの粒度で記録し、出力結果から次に何を調べるかを自分で決められるようにする。

到達目標：Railsの処理を止めずに、値の流れと分岐をログで追跡できる

0. この単元で身につけること

ゴールは、Rails.logger.debugという名前を知ることではありません。次の一連の行動を、自分で選べることです。

症状を記録 境界を選ぶ ログを書く 出力を読む 次を決める

知識

Logger、ログレベル、文字列補間、inspect、タグ、環境ごとの出力先を説明できる。

技能

Controller・View・Modelのどこに、どの値を、どの形式で記録するか選べる。

判断

「値がない」「型が違う」「分岐が違う」「関連先がない」をログから区別できる。

習慣

タグを付け、最小限の観測を行い、原因確認後に一時ログを削除できる。

1. Loggerは「サーバー側の観測ノート」

ブラウザの画面に表示するdebugヘルパーに対して、Rails.logger.debugはRailsサーバー側へメッセージを残します。

ブラウザのdebug
Viewが最後まで生成できたとき、HTMLとして見える
p value
Rubyの標準出力へ表示し、実行環境によってターミナルなどで見る
Rails.logger.debug
Railsのログへ記録する。後で検索でき、画面が完成しなくても前段の記録を残せる
# Controller、Model、Viewなど、Railsの処理中で実行する
Rails.logger.debug("[DEBUG-reservations] index started")
考え方：画面がエラーで表示されないときは、ブラウザ表示ではなく、エラーが起きる前のサーバー側の境界へLoggerを置く。

参考：Rails Guides: The Logger

2. 1行の構造を分解する

Rails.logger.debug("[DEBUG-index] count=#{@reservations.size} ids=#{@reservations.map(&:id).inspect}")
Rails
Railsアプリケーション全体の入口
logger
ログへ書き込む担当オブジェクト
debug
詳細な開発用メッセージとして記録するメソッド
"..."
ログに書くメッセージ。固定文と値を組み合わせる
[DEBUG-index]
自分の観測を検索するための目印
#{...}
Rubyの式を文字列へ埋め込む
inspect
配列やHashなどの中身を、構造が分かる形で文字列化する

悪い観測

Rails.logger.debug("予約")

何を確認したいログか、値が何だったか分からない。

良い観測

Rails.logger.debug(
  "[DEBUG-index] " \
  "count=#{@reservations.size} " \
  "ids=#{@reservations.map(&:id).inspect}"
)

場所・件数・IDが分かり、次の確認につながる。

3. 「何を出すか」は質問から決める

先にログ文を書かず、知りたいことを質問にします。その質問に必要な最小限の値だけを出します。

集合は届いたか？
クラス・件数・ID
1件は何者か？
クラス・ID・主な外部キー
値が空か？
値そのもの・nil?・必要なら型
関連先があるか？
関連先のID・関連先のクラス
分岐のどちらへ入ったか？
分岐名・条件値・成功／失敗
保存できたか？
ID・成功結果・errors.full_messages
# 値の意味を残す。巨大なオブジェクトを毎回丸ごと出さない
Rails.logger.debug(
  "[DEBUG-create] " \
  "reservation_id=#{@reservation.id.inspect} " \
  "hotel_id=#{@reservation.hotel_id.inspect} " \
  "sum_price=#{@reservation.sum_price.inspect}"
)
最小観測の原則：1回のログで全部を出そうとせず、「この仮説を判定するために必要な値は何か」を一つずつ決める。

4. 値の型と形を見えるようにする

ログで値を見るときは、「表示された文字」だけでなく、Rubyが何として扱っているかも必要です。

Rails.logger.debug "[DEBUG-value] value=#{value.inspect}"
Rails.logger.debug "[DEBUG-value] class=#{value.class.name}"
Rails.logger.debug "[DEBUG-value] nil=#{value.nil?}"

# 配列やHashはinspectで構造を残す
Rails.logger.debug "[DEBUG-rows] rows=#{rows.inspect}"
Rails.logger.debug "[DEBUG-params] keys=#{params.to_unsafe_h.keys.inspect}"
注意：パスワード、認証トークン、カード情報、個人情報をそのままログへ出さない。Params全体の記録も、何が含まれるか確認してから行う。

nil

値が存在しない状態。nil?やinspectで明示的に確認する。

空文字列

""はnilではない。画面入力では「空」に見えても別の値である。

文字列の数字

"2"は整数2とは違う。HTTPパラメータは文字列として届くことがある。

Relationと配列

Reservation.allは複数件を扱うRelation。1件のreservationとは役割が違う。

5. ログレベルを使い分ける

Loggerには重要度の段階があります。デバッグ中の詳細情報は通常debugですが、すべてを同じレベルで出すわけではありません。

debug

開発中に値や処理順を細かく見る。通常、最も詳細な観測。

info

通常の処理が進んだことなど、運用上も意味がある情報。

warn

処理は続けられるが、想定外・注意が必要な状態。

error

処理に失敗した、またはユーザー操作を完了できなかった状態。

fatal

アプリケーションを継続できない重大な状態。

表示されないとき

環境のログレベルがinfo以上なら、debugが出ないことがある。Loggerの設定と実行環境を確認する。

Rails.logger.debug("[DEBUG-index] detailed value")
Rails.logger.info("[INFO-index] page rendered")
Rails.logger.warn("[WARN-create] unexpected input")
Rails.logger.error("[ERROR-create] save failed")

参考：Rails Guides: Log Levels

6. どこに置くか：境界を記録する

リクエスト到着 DB取得後 加工・計算後 分岐の直前 保存・render後

Controller

リクエスト、params、DB取得結果、分岐、render／redirectの前後を調べる。

Model

値の計算、validation、callback、保存前後を調べる。

View

Viewまで届いた値、eachの1件、関連先、画像やリンク生成の直前を調べる。

境界の考え方

「どこからどこへ値が渡ったか」を区切る。全行にログを置かない。

def index
  Rails.logger.debug "[DEBUG-index] start"
  @reservations = Reservation.all
  Rails.logger.debug(
    "[DEBUG-index] loaded count=#{@reservations.size} " \
    "ids=#{@reservations.map(&:id).inspect}"
  )
end
今回の予約一覧への適用：まずControllerで@reservationsの集合を確認し、次にViewのeach内で1件のreservationを確認する。その後、必要ならhotel、avatarへ一段ずつ進む。

7. ログの読み方：行を足すだけで終わらせない

ログを出したら、次の4列に分けて読みます。

時系列
どのログが先に出たか。処理がどこまで進んだか。
場所
タグ、Controller／Model／View、IDなど。
値
件数、型、nil、ID、分岐条件。
未確認
正常だったものと、まだ疑うべきものを分ける。
[DEBUG-index] start
[DEBUG-index] loaded count=1 ids=[7]
[DEBUG-view] reservation_class=Reservation id=7 hotel_id=3
[DEBUG-view] hotel_class=Hotel id=3
# この後のログがない場合、次の処理の直前か、その処理自体を調べる
解釈の例：このログから「DBに1件ある」だけでなく、「Controllerで1件を取得し、Viewのeach内でもReservation id=7として届いた」まで確認できる。次は未確認の関連や画像処理へ進む。

8. 実際のログを読むための操作

開発サーバーのターミナル

サーバーを起動しているターミナルに、リクエストログとLoggerの出力が流れることがあります。まずタグで見つけます。

rg "\[DEBUG-index\]" log/development.log

rgは指定した文字列をログファイルから検索します。何も出なければ、タグ・環境・ログレベル・実行されたアクションを確認します。

新しいログを追いかける

tail -f log/development.log

tail -fはファイル末尾を表示し続けます。ブラウザで操作し、タグ付きの新しい行が追加されるかを確認します。終了はCtrl + Cです。

ログが出ないときの順番

  1. そのリクエストが目的のController／actionへ届いたか。
  2. Loggerの行より前で例外が起きていないか。
  3. タグを検索しているファイルが、実際の環境のログか。
  4. ログレベルがdebugを表示する設定か。
  5. コードを変更した後、リクエストをもう一度送ったか。

参考：Rails Guides: The Logger / Rails Guides: Sending Messages

9. 実践ラボ：ログ文を組み立てる

目的を選ぶと、必要な値・置き場所・読み方が表示されます。これは実際のアプリへは接続しません。

10. 問題集（全16問）

1〜8問は選択式、9〜16問は自分でログ文を考える練習です。先に答えを決めてからボタンを押してください。

問題1：Loggerの役割

Rails.logger.debugの主な役割は？

Loggerは観測情報を記録します。値を変更したり、エラーを解決したりする機能ではありません。

問題2：画面が表示されないとき

Viewの後半でエラーが起き、ブラウザにdebug結果が出ない。最初の観測場所は？

View全体が完成しないと途中のHTMLは届きません。サーバー側の前段をLoggerで観測します。

問題3：タグの目的

[DEBUG-index]を付ける一番の目的は？

タグはログの検索、時系列の追跡、一時ログの削除に役立ちます。

問題4：配列の表示

配列idsの中身を構造が分かる形で記録するには？

inspectは配列やHashなどの構造を含めて確認しやすい文字列にします。

問題5：countと1件

@reservations.sizeを出した次に、each内の値を調べる理由は？

集合が1件でも、1件の関連先や属性が正常とは限りません。境界を分けて観測します。

問題6：型の確認

値がnilかどうかだけでなく型も知りたい。何を追加する？

値そのものとクラスを組み合わせると、nil・String・Integer・Dateなどを区別できます。

問題7：ログレベル

開発中に詳細な値を調べるための標準的なレベルは？

debugは詳細な開発用情報に使います。warnやerrorは注意・失敗の意味を持たせます。

問題8：ログが出ない

Loggerの行を書いたのに検索結果がない。最初に確認しないものは？

ログがないだけでDBを作り直す必要はありません。まず記録先と実行経路を確認します。

問題9：集合のログを書く

Controllerで@reservationsの件数とID一覧を確認したい。必要な情報を含むLoggerの1行を考えてから表示を押してください。

観点：タグ、size、ID一覧。例：Rails.logger.debug "[DEBUG-index] count=#{@reservations.size} ids=#{@reservations.map(&:id).inspect}"

問題10：each内の1件を書く

Viewのeach内で、reservationのクラス・ID・hotel_idを確認するログを考えてください。

観点：eachの内側、class.name、id、hotel_id。例：Rails.logger.debug "[DEBUG-view] class=#{reservation.class.name} id=#{reservation.id.inspect} hotel_id=#{reservation.hotel_id.inspect}"

問題11：関連を一段ずつ追う

reservation.hotel.avatarが怪しい。まずreservationとhotelを分けて観測するログを考えてください。

観点：reservationのhotel_idを確認し、hotel取得後にhotelのIDやクラスを見る。関連を一つの長い式で済ませない。

問題12：成功／失敗の分岐を書く

@reservation.saveの成功・失敗のどちらに入ったかを後から読めるログを考えてください。

観点：成功側と失敗側でタグや文言を変える。失敗側ではerrors.full_messagesも確認する。

問題13：最小観測

原因が分からないときのログの増やし方として適切なのは？

ログが多すぎると時系列と重要な値が埋もれます。仮説ごとに必要な観測を選びます。

問題14：安全なログ

ログへ出す情報として最も注意が必要なのは？

ログは保存・共有される可能性があります。秘密情報や個人情報は記録しない、またはマスキングします。

問題15：ログの時系列

「Aのログはあるが、Bのログがない」から考えられることは？

ログの間を新しい境界として調べます。Aがあることは、B以降の成功を保証しません。

問題16：デバッグ終了

原因を確認して修正した後のLoggerの扱いは？

一時的な詳細ログはノイズや情報漏えいの原因になります。タグで検索して片付けます。

11. 自力で使えるかの確認

次の状況で、Loggerを使う場所・値・レベルを口頭またはメモで説明できれば、この単元の入口を卒業です。

  1. ブラウザには何も表示されず、Viewの後半でエラーが出る。
  2. Controllerの@reservationsは1件だが、画像表示で失敗する。
  3. 保存処理が成功したか失敗したか分からない。
  4. ログを出したが、どのリクエストのものか分からない。
  5. debugログが開発環境で見つからない。
説明の型：「私は○○を知りたいので、△△の直後に、タグ付きで□□（値・型・ID）をdebugレベルで出す。ログにAがあればBを調べ、なければCを確認する」と説明する。

12. 実践後の片付け

  1. タグで自分の一時ログを検索する。
  2. 必要な観測結果をメモする。
  3. 不要なLogger行とViewのdebug表示を削除する。
  4. 同じ操作を再実行して、元の症状が消えたことを確認する。
  5. ログに秘密情報が残っていないか確認する。
rg "\[DEBUG-(index|view|create)\]" app log
# 見つかった一時ログを確認してから削除する
