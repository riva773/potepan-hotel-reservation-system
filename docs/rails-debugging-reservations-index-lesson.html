Railsデバッグ入門：
予約一覧の「nil」を追う

「DBには1件あるのに、ビューではnilになる」「debugを置いたのに、どこで壊れたか分からない」という状態から、事実を一つずつ観測して原因を絞る。

今日のゴール：エラーを見たときに、値の流れ・失敗行・次の観測を自分で決められる

1. デバッグとは何をすることか

デバッグは、最初から原因を当てる作業ではありません。「どの値が、どの境界で、予想と違ったか」を小さな観測で狭める作業です。

症状を記録 失敗行を特定 値を観測 仮説を絞る 修正後に再確認
覚える型：「考え方 → 行動・観測 → 目的 → 結果の解釈」の順で進める。debug文を増やすこと自体が目的ではない。

2. 今回の予約一覧で、値はどこを通るか

DBの行数と、ビュー内の変数は同じものではありません。間にController、コレクション、eachの1件が存在します。

Reservation.count
DBにある予約行の数。ビューの変数の中身までは保証しない。
@reservations = Reservation.all
Controllerがビューへ渡す、予約の集合（Relation）。
each do |reservation|
集合から1件ずつ取り出した、その周回だけの変数。
reservation.hotel
予約に紐づくホテル。予約そのものとは別のオブジェクト。
reservation.hotel.avatar
さらにホテルの画像添付。ここにもnilや未添付という状態があり得る。
# app/controllers/reservations_controller.rb
def index
  @reservations = Reservation.all
end

# app/views/reservations/index.html.erb
@reservations.each do |reservation|
  reservation.hotel.avatar
end
重要：count == 1は「集合に1件ある」という観測です。「その1件のhotelが存在する」「avatarが添付済み」「ビューのこの変数がその1件を指す」までは、別々に確認します。

3. エラー文は「誰が」「何を」失敗したか読む

undefined method 'x' for nil:NilClass

xを呼び出そうとした左側の値がnil。まず「どの値がnilか」を探す。

ArgumentError

メソッドへ渡した引数の数や形が想定と違う可能性。値の中身より、呼び出し方を確認する。

TypeError

型の組み合わせが合わない可能性。文字列・整数・日付・nilなど、両側の型を確認する。

スタックトレース

呼び出しの道筋。最初に出てくる自分のファイルの行を、まず調査対象にする。

推測の注意：「Reservation.countが1だからreservationも必ず1件」とは言えない。エラー行に実際に書かれた式の、左側の値を確認する。

参考：Rails Guides: Debugging Rails Applications

4. 観測場所を選ぶ：ブラウザかログか

同じ「値を見る」でも、どこで見るかで分かることが違います。

ブラウザに出す：debug

Viewまで処理が到達したとき、HTMLの中にオブジェクトを表示できる。画面でその場の値を確認する。

<%= debug @reservations %>

<% @reservations.each do |reservation| %>
  <%= debug reservation %>
<% end %>

ログに出す：Rails.logger.debug

ControllerやViewの処理中に、サーバー側へ観測結果を残す。タグを付けると後で見つけやすい。

Rails.logger.debug(
  "[DEBUG-reservations] " \
  "count=#{@reservations.size} " \
  "ids=#{@reservations.map(&:id).inspect}"
)
pとの違い：p valueはRubyの値を標準出力へ表示し、値自身を返す。debug valueはRailsのView Helperで、ブラウザに見やすい形で出す。

参考：Rails Guides: View Helpers for Debugging / Rails Guides: The Logger

5. 今回のコードでの正しい観測順

  1. まずエラー画面を見る。例外名、メッセージ、最初の自分のファイルの行番号を記録する。
  2. Controllerの境界を見る。@reservationsが本当に取得されているか、クラス・件数・IDを確認する。
  3. eachの中で1件を見る。reservationが何者か、IDがあるかを確認する。eachの外で同じ名前を見ても、1件の確認にはならない。
  4. ドットの連鎖を分解する。reservation.hotel.avatarを一気に評価せず、reservation、hotel、avatarの順に確認する。
  5. 添付状態を確認する。Active Storageの画像は、関連オブジェクトが存在することと、ファイルが添付済みであることを分けて見る。
  6. 一つだけ変えて再現する。観測用の行を一度に増やしすぎず、どの観測がどの仮説を判定するか明確にする。
# Controllerで集合を観測する例
Rails.logger.debug "[DEBUG-reservations] class=#{@reservations.class.name}"
Rails.logger.debug "[DEBUG-reservations] count=#{@reservations.size}"
Rails.logger.debug "[DEBUG-reservations] ids=#{@reservations.map(&:id).inspect}"

# Viewではeachの中で、その周回のreservationを観測する
<% @reservations.each do |reservation| %>
  <%= debug reservation %>
  <%= debug reservation.hotel %>
  <%= debug reservation.hotel.avatar.attached? %>
<% end %>
観測結果の解釈：reservationがReservationなら、次は関連先を疑う。reservation自体がnilなら、eachの位置・変数名・Viewへ渡す処理を疑う。

観測ポイントA：eachの外か、中か

デバッグ表示を置く位置が、調べたい値のスコープと一致しているかを確認する。reservationという名前は、eachのブロック引数として初めて1件を指す。

観測ポイントB：エラー行はどの式か

もしエラー行が画像表示なら、reservationがnilだと決めつけず、reservation.hotel、reservation.hotel.avatarも候補にする。

観測ポイントC：ERBの出力記号

<%= ... %>は式の返り値をHTMLへ出力し、<% ... %>は処理だけを実行する。eachのような制御処理をHTMLへ出す必要があるかを考える。

関連：Rails Guides: Active Record Basics - Read / Rails Guides: Active Storage - has_one_attached

8. 演習問題（全8問）

先に自分の答えを考えてから選択肢を押してください。正解後も、なぜその観測になるかを言葉にしてみます。

演習1：countが教えること

Reservation.count == 1から確実に言えることは？

countはDBの行数の観測です。Controllerの変数、eachの1件、関連先は別々に確認します。

演習2：reservationを観測する場所

eachで取り出した予約1件を調べる場所は？

ブロック引数reservationは、eachの周回の中で1件を指します。

演習3：ブラウザ表示

Viewまで到達したとき、オブジェクトをブラウザに見やすく表示するRailsの方法は？

debug helperはオブジェクトをpreタグ内に表示するView用の観測手段です。

演習4：nilエラーの読み方

undefined method 'persisted?' for nil:NilClassで最初に考えることは？

メソッド名ではなく、メソッドを受け取った左側の値を特定します。

演習5：reservationが正常な場合

each内でreservationがReservation id=1と分かった。次の観測は？

対象が正常なら、次のドットの右側やメソッド引数へ境界を一つ進めます。

演習6：ログの目的

ログに[DEBUG-reservations]のような印を付ける目的は？

タグは観測結果の検索と、デバッグ行の後片付けに役立ちます。

演習7：推測と観測

「countが1だから問題ない」と思った次にすることは？

DB、Controller、Viewの各境界で同じ値が保たれているかを確かめます。

演習8：デバッグ終了

原因を直して再現しなくなった後にすることは？

元の症状が消えたこと、別の問題を隠していないこと、観測コードが残っていないことを確認します。

9. 自分のアプリで実行するチェックリスト

  1. エラー画面から、例外名・メッセージ・最初の自分のファイル行をメモする。
  2. その行の式を、左から右へ分解する。特にドットが続く式を一気に読まない。
  3. Controllerで集合のクラス・件数・IDを一度だけログに出す。
  4. Viewでは、調べたい変数が有効なスコープの中にdebugを置く。
  5. 観測結果を「正常だったもの」と「まだ未確認のもの」に分ける。
  6. 次の一手を一つだけ実行し、同じ操作で再現する。
  7. 修正後、元の操作を再実行して症状が消えたことを確認する。
  8. タグ付きログと一時的なdebug表示を削除する。
最後に説明できれば合格：「どのリクエストで、どのControllerが、どの値をViewへ渡し、どの行のどの値が予想と違った。だから、そこを確認・修正した」と言える。
