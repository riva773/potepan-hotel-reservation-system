TurboとFetch通信を
原理から学ぶ

「Networkにfetchと出る」「Railsログでは200なのに画面が変わらない」という現象を、ブラウザ・JavaScript・Railsサーバーの役割に分けて説明できるようになる。

今日のゴール：Turboを切る理由を、コードではなく通信の流れで説明できる

1. まず、画面が変わる仕組み

Webアプリでは、クリックしただけでサーバーのデータが変わったり、別画面が表示されたりしているように見えます。実際には、ブラウザとサーバーがリクエストとレスポンスを交換しています。

ブラウザで操作 HTTPリクエスト Railsが処理 レスポンス 画面を更新

ブラウザ

HTMLを表示し、クリックやフォーム送信を開始する。画面を書き換える役割も持つ。

サーバー

URL・HTTPメソッド・パラメータを受け取り、Controllerを動かしてHTMLなどを返す。

リクエスト

「このURLへ、この方法で、このデータを送る」という依頼。POSTは登録・送信などで使う。

レスポンス

サーバーからの返事。ステータスコード、ヘッダー、本文（HTMLなど）を含む。

2. Fetchとは何か

Fetch APIは、ブラウザ上のJavaScriptがネットワーク越しにリクエストを送り、レスポンスを受け取るための仕組みです。Fetchそのものは「画面遷移」ではなく、「通信」を担当します。

fetch("/reservations/confirm", {
  method: "POST",
  body: formData
})
fetch(...)
JavaScriptから通信を開始する
method: "POST"
データを送信するリクエストにする
Response
サーバーから返ってきたステータスや本文を表す
画面の更新
レスポンスをどう画面に反映するかは別途必要
重要：Fetchで通信が成功しても、画面が自動で別ページになるとは限りません。通信と画面更新は別の仕事です。

参考：MDN Fetch API

3. Turboとは何か

Turboは、Railsの画面遷移やフォーム送信を、JavaScriptで扱いやすくする仕組みです。Rails 7系ではHotwireの一部として利用されます。

Turboの中心的な機能であるTurbo Driveは、リンククリックやフォーム送信を監視します。そして、通常のブラウザ任せの処理の代わりに、裏側でリクエストを送り、返ってきた内容を使ってページを更新します。

Turboを使わない通常送信

  1. フォームを送信する
  2. ブラウザがページ全体をサーバーへ移動する
  3. 返ってきたHTMLを新しいページとして表示する

Turboを使う送信

  1. Turboがフォーム送信を受け取る
  2. Fetch通信でサーバーへ送る
  3. レスポンスの種類に応じて画面を更新する

参考：Turbo Handbook: Navigate with Turbo Drive

4. 今回の予約確認で起きたこと

あなたのホテル詳細ページのフォームをクリックしたときの処理を、順番に並べます。

  1. ホテル詳細ページのフォームで「予約する」を押す。
  2. Turboが送信を受け取る。通常のページ遷移を、Turboの処理に任せる。
  3. Fetch通信でPOST /reservations/confirmを送る。
  4. RailsがReservationsController#confirmを実行する。
  5. Railsログにas TURBO_STREAM、Completed 200 OKが出る。
  6. レスポンスには確認ページの内容がある。しかし、POSTに対する200の通常renderでは、Turboは現在のURLにとどまる。
Started POST "/reservations/confirm"
Processing by ReservationsController#confirm as TURBO_STREAM
Rendering reservations/confirm.html.erb
Completed 200 OK
このログから分かること：Railsの処理とレスポンス生成は成功している。一方、画面遷移の成否は、ブラウザがそのレスポンスをどう扱ったかまで確認する必要がある。

5. なぜ200なのに画面が変わらないのか

Turbo Driveは、フォームのPOST送信後にサーバーがリダイレクトを返す流れを基本としています。POSTの処理結果を200で直接renderした場合、リロード時にPOSTが再送信される危険があるため、Turboは現在のURLにとどまります。

通常のHTMLを表示したい

そのフォームだけTurboを無効にし、ブラウザの通常送信に任せる。返ってきた確認ページを新しいページとして表示する。

Turboで部分更新したい

<turbo-stream>など、Turboが理解できる形式のレスポンスを返し、指定した部分だけ更新する。

<%= form_with ..., data: { turbo: false } do |f| %>

上の指定は「このフォームではTurboによるFetch処理を使わない」という意味です。今回のように確認ページへ普通に移動したい場合に、仕組みを単純にできます。

参考：Turbo Handbook: Redirecting After a Form Submission / Disabling Turbo Drive

7. 演習問題（全8問）

まず自分の答えを考えてから、選択肢をクリックしてください。正解・不正解と理由が表示されます。

演習1：Fetchの担当

Fetch APIが直接担当するものはどれですか？

Fetchはリクエストを送り、レスポンスを受け取る仕組みです。受け取った内容を画面に反映する処理は別の役割です。

演習2：Turboの位置

Turboは主にどこで動いて、フォーム送信を監視しますか？

Turboはブラウザで動くJavaScriptの仕組みです。Rails側はTurboが送ったリクエストを通常のControllerで処理します。

演習3：NetworkのType

NetworkタブのTypeがfetchだったとき、最も直接的に分かることはどれですか？

Typeは通信の方法を示します。レスポンスの中身やDB保存の成否、画面更新の成否まではTypeだけでは分かりません。

演習4：Railsログの読み方

Completed 200 OKから分かることはどれですか？

200はHTTPレスポンスの成功ステータスです。画面反映やDB保存まで確認するには、レスポンス・画面・SQLログも見ます。

演習5：as TURBO_STREAM

Processing ... as TURBO_STREAMの意味として近いものはどれですか？

RailsがリクエストをTurbo Stream形式として受け取った、という意味です。Controllerが実際にTurbo Streamタグを返しているかはResponse本文で確認します。

演習6：POST後の200 render

TurboフォームのPOSTに対して、redirectではなく200で通常のHTMLをrenderした場合の説明はどれですか？

POSTの再送信を避けるため、Turboは200の直接renderでは現在のURLにとどまります。今回の画面が変わらなかった現象とつながります。

演習7：Turboを無効にする指定

フォーム単位でTurbo Driveを無効にする指定はどれですか？

data-turbo="false"をHTMLに付ける指定です。Railsのフォームヘルパーではdata: { turbo: false }と書けます。

演習8：調査の順番

画面が遷移しないとき、原因を絞る確認の順番として最もよいものはどれですか？

ブラウザが何を送ったか、Railsがどう処理したか、何を返したか、ブラウザがどう反映したかを順番に分けると、推測で修正せずに済みます。

8. 自分のアプリで確認するチェックリスト

  1. Networkで、Request URLが/reservations/confirmか確認する。
  2. Request MethodがPOSTか、Form Dataにreservationがあるか確認する。
  3. Railsログで、どのController#actionが実行されたか確認する。
  4. as TURBO_STREAMかas HTMLかを確認する。
  5. Statusが200か、リダイレクトなら3xxかを確認する。
  6. Response本文が普通のHTMLか、<turbo-stream>かを確認する。
  7. 「サーバーが成功した」と「ブラウザ画面が更新された」を別々の事実として記録する。
説明できれば合格：「Turboがフォーム送信を受け取り、FetchでPOSTした。Railsは200を返したが、POST後の通常renderだったためTurboはURLを変えず、画面に確認ページを表示しなかった」のように、役割を分けて言える。
